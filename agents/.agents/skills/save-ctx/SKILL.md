# Save Context

Write a detailed context summary to a markdown file in the current working
directory:

`context-saves/context-<harness>-YYYY-MM-DD-HHMMSS.md`

Use the agent harness name for `<harness>`: `claude-code`, `codex`, or
`opencode`. If the harness is unclear, use a short lowercase identifier.
Create `context-saves/` if needed. Use the current local timestamp.

The reader is a fresh agent, possibly in a different harness, that sees nothing
of this conversation. Anything not written in the file is lost.

## Before writing

Check the real workspace state instead of relying on recollection. If the
working directory is a git repository, run `git status --short` and
`git diff --stat` (plus `git diff --cached --stat` when something is staged),
and base the Changes Made and Current State sections on that output. Note the
current branch and the last commit. If it is not a git repository, say so in
Current State.

## File contents

Start the file with a one-line origin header:

`> Generated by <harness> (<model>) on YYYY-MM-DD HH:MM`

Follow it with this note to the reader, verbatim:

`> To resume: run git status and git diff first and check them against Changes Made and Current State below. If they disagree, trust the files and tell the user. Then continue from Remaining Work.`

Include these sections:

## Objective

The overall goal or task currently being worked on.

## Standing Instructions

Everything the user said during the session that still applies to the remaining
work: things to avoid, preferred approaches, constraints, how they want results
reported. Quote the user's wording where it matters. Write "None" if there are
none.

Record only what was said in this session. Leave out rules that the project's
or the user's instruction files already state (`AGENTS.md`, `CLAUDE.md`, shared
core instructions): the next agent loads those itself, and repeating them
buries the session-specific ones.

## Decisions Made

Technical decisions and design choices established during the session. Include
reasoning when it matters for resuming work, and options that were considered
and rejected, with the reason.

## Changes Made

Every file created, modified, or deleted. For each, briefly describe what
changed and why. Include paths. State which changes are committed, staged, or
unstaged.

## Current State

The last completed step and the current codebase or workspace state relative to
the goal. If the save happens in the middle of an edit or a multi-step change,
say so in the first line, and name what is half-done and what would finish it.

## Blockers & Issues

Problems encountered, unresolved errors, open questions, or required user input.

## Remaining Work

Concrete next steps to complete the objective, in order. Include paths, function
names, commands, or implementation details when known.

## Key Context

Non-obvious details a fresh session needs: environment facts, quirks,
important file locations, conventions, and gotchas discovered during the work.
Leave out what the instruction files or saved memory already record; include
only what this session found.

## After writing

Do not print the file's contents: the note is written once, to the file. Reply
with only:

- the path of the saved file;
- three or four lines covering the objective, the current state, and the next
  step, so the user can spot a wrong note without opening it;
- one closing line: run `load-ctx` in the next session to continue.

The digest is a check for the user, not a second copy. Keep the file itself as
detailed as the work needs.
